# Phase 1 — Data Model: Downloads Manager

**Spec**: [spec.md](spec.md) · **Plan**: [plan.md](plan.md) · **Research**: [research.md](research.md) · **Date**: 2026-09-10

The feature adds **one persisted table** and **two purely computed shapes**. The split is the whole point of the hybrid decision: what the app durably owns is *identity and metadata*; what the platform owns is *live transfer state*, and that is never written down.

---

## 1. Persisted — `DownloadRecordEntity` (new, Room)

Follows the entity conventions Spec 005 established: table and column names as `const val`s in the companion object (Constitution §III forbids the raw strings appearing inline), `@ColumnInfo` on every field, autogenerated primary key.

| Field | Type | Null? | Meaning |
|-------|------|-------|---------|
| `id` | `Long` | no (PK, autogenerate) | The app's own identifier for the record. |
| `sourceUrl` | `String` | no | The address the file was fetched from. Shown by "copy link" (FR-033); never re-fetched automatically. |
| `fileName` | `String` | no | The sanitised name as written to disk (FR-004, FR-005). Already reduced to a single path segment before it reaches this field. |
| `mimeType` | `String` | no | The determined content type (FR-006). Empty string when nothing trustworthy was available — never null, so the mapper stays total. |
| `createdAt` | `Long` | no | Epoch milliseconds at the moment the platform accepted the transfer. Drives the reverse-chronological order (FR-019) and the displayed time (FR-020). |
| `transferHandle` | `Long` | no | The platform service's transfer handle (column `transfer_handle`). The join key for every live-status read, and the argument to cancellation (FR-036). |
| `localUri` | `String` | yes | The content URI of the finished file, recorded once the transfer completes. Null while in flight. Used to open the file (FR-025, FR-026) and to test file presence (FR-024a, FR-029). |

**Indices**: one on `createdAt` — the list's only ordering (FR-019), mirroring how Spec 005 indexed `history_entries.visited_at`. A second on `transferHandle` is **not** added: lookups by handle happen in the other direction (records drive queries to the platform, not the reverse), and at the 500-record envelope of A14 an index would cost writes to save nothing measurable.

**Foreign keys**: none. A download record is not owned by a tab, a bookmark, or a history entry, and outlives all of them.

**Invariants**
- A row exists **only** for a transfer the platform service accepted (FR-008b). Nothing is written before the handle comes back. This is what makes the FR-024a inference sound — a row with no handle is impossible, so "handle unknown" always means *forgotten*, never *never-started*.
- `transferHandle` is unique in practice because the platform allocates it, but **no unique constraint is declared**: a stale value from a service that reset its counters must not be able to make an insert fail and lose the user's download.
- Nothing about incognito is stored (FR-014a). There is deliberately no column for it.
- No live state — no progress, no byte counts, no running/paused flag (FR-015, FR-024c).
- **Naming**: the field is `transferHandle`, not the platform class's own identifier name. FR-054 exists to keep the download service behind an abstraction, and a pure-Kotlin domain model that names the concrete Android class in one of its fields would undercut that at the vocabulary level even though no import is involved. The gateway's parameters use the same word, so one term spans the whole feature.

## 2. Schema migration v1 → v2 *(FR-016, FR-017)*

**The project's first real migration.** Additive only.

```text
version 1 (Spec 005)                      version 2 (this spec)
├── bookmarks                             ├── bookmarks                 ← untouched
├── bookmark_folders                      ├── bookmark_folders          ← untouched
├── history_entries                       ├── history_entries           ← untouched
└── tabs                                  ├── tabs                      ← untouched
                                          └── download_records          ← NEW
                                              + index on created_at     ← NEW
```

Rules this migration must obey, all inherited from Spec 005:

- `AppDatabase.SCHEMA_VERSION` goes `1` → `2`; the `entities` array gains the new entity.
- The migration is **registered explicitly** on the database builder. `fallbackToDestructiveMigration*` must remain absent — `git grep` in `app/src/main/` returns zero matches today and must still return zero at merge.
- `app/schemas/…/2.json` is generated by the build and **committed to git**. Today that directory holds only `1.json`.
- An automated test proves a database created at v1, populated with rows in all four existing tables, opens at v2 with every row intact and readable (FR-017). This uses `androidx.room:room-testing`, which is **already in the version catalog and already wired** (see [research.md](research.md) R5) — no dependency is added.

Because no existing table is named in the migration, there is no path by which existing user data can be altered or lost. That property is what makes this an acceptable first exercise of the strict policy.

## 3. Computed — `DownloadStatus` (domain, never persisted)

Read from the platform service at display time and discarded. Modelled as a sealed type so that "which fields are meaningful" is carried by the type rather than by nullability convention.

| Variant | Carries | When |
|---------|---------|------|
| `Pending` | — | Accepted, not yet transferring. |
| `Running` | `bytesSoFar: Long`, `totalBytes: Long?` | In flight. `totalBytes` is null when the server declared no length — the UI then shows indeterminate progress rather than a fake percentage. |
| `Paused` | `bytesSoFar: Long`, `totalBytes: Long?` | The platform paused it (network loss, waiting for Wi-Fi). |
| `Complete` | — | Finished successfully. |
| `Failed` | `cause: DownloadFailureCause` | Ended in failure. |
| `Cancelled` | — | Removed by the user before completion. |
| `Missing` | — | **Derived, not reported.** Emitted when the handle is unknown to the service *and* the recorded file is absent (FR-024a). |

`DownloadFailureCause` is a small sealed set — `InsufficientSpace`, `NetworkFailure`, `Generic` — mapping to localized messages the way Spec 007's `ErrorReason` already does. Only causes the user can act on get their own variant (FR-022); everything else collapses into `Generic` rather than surfacing a platform error code the user cannot use.

**Terminal states** for the purposes of the FR-034a action matrix: `Complete`, `Failed`, `Cancelled`, `Missing`. `Pending`, `Running` and `Paused` are in-flight.

### Status resolution rule (FR-024a)

```text
query the platform service by transferHandle
├── row returned  → map its state directly to a DownloadStatus variant
└── no row        → the handle is forgotten; fall back to the file:
                    ├── recorded file present → Complete
                    └── recorded file absent  → Missing
```

The fallback deliberately never yields `Pending`, `Running` or `Paused` — a forgotten transfer cannot be in flight. Recorded as an explicit prohibition in FR-024a so the mapping is testable rather than incidental.

**Known limitation (A15)**: a download that failed long ago and was then pruned resolves to `Missing`, identical to one that succeeded and whose file the user later deleted. Accepted during clarification; the remedy offered to the user is the same in both cases.

## 4. Computed — `DownloadListItem` (presentation, never persisted)

The pairing of one `DownloadRecord` with its freshly-resolved `DownloadStatus`. This is what a row renders and what the action matrix is evaluated against. It has no storage and no identity of its own beyond the record's.

Derived per item, not stored:
- **Displayed size** — from `totalBytes` while in flight, from the file otherwise; formatted per locale (FR-050).
- **Available actions** — computed from the status and file presence by the FR-034a matrix, not baked into the item.

## 5. Domain models (pure Kotlin, no Android imports)

| Model | Shape |
|-------|-------|
| `DownloadRecord` | 1:1 mirror of the entity — `id`, `sourceUrl`, `fileName`, `mimeType`, `createdAt`, `transferHandle`, `localUri: String?`. Mapped by a dedicated mapper, matching how `HistoryEntryMapper` mirrors its entity. |
| `DownloadStatus` | The sealed type in §3. |
| `DownloadFailureCause` | The sealed cause set in §3. |
| `DownloadListItem` | `record: DownloadRecord` + `status: DownloadStatus`. |
| `DownloadRequest` | The value handed to the gateway when starting a download: `sourceUrl`, the sanitised `fileName`, `mimeType`, and the user agent / referer the engine supplied. Constructed in the domain layer so the sanitisation in FR-005 is unit-testable on the JVM. |

---

## 6. Presentation state

- **`DownloadsUiState`** (immutable `data class`): `items: List<DownloadListItem>`, `pendingActionSheetTarget: DownloadRecord?`, `pendingDeleteConfirmation: DownloadRecord?`, `isLoading: Boolean`. Follows the project's `StateFlow<UiState>` convention.
- **`DownloadsEvent`** (sealed, one-shot): `LinkCopied`, `NoAppCanOpenFile`, `FileMissing(record)`, `DownloadServiceUnavailable`, `StoragePermissionDenied(permanently: Boolean)`, `DownloadStarted(fileName)`, `OperationFailed(throwable)`. Emitted on a dedicated `SharedFlow` with `replay = 0`, `extraBufferCapacity = 1`, `onBufferOverflow = DROP_OLDEST` — the channel policy Spec 013 set and Spec 014 mirrored.

`DownloadStarted` is emitted from the browser screen's side of the feature, not the Downloads screen, because FR-002 requires the confirmation to appear over the page the user is still on.

---

## 7. What is deliberately absent

- No incognito column or flag anywhere (FR-014a).
- No persisted progress, byte counts, or transfer state (FR-015).
- No terminal-outcome column — rejected during clarification in favour of the file-presence inference (A15).
- No retention window, row cap, or pruning job. Unlike history — which Spec 014 had to bound at 90 days after measuring unbounded growth — records here accrue only by deliberate user action (A9, A14).
- No unique constraint on `transferHandle` (see §1 invariants).
- No foreign key to tabs, bookmarks, or history.
